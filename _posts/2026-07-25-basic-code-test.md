이 글을 쓰게 된 계기는 간단하다. Codex를 이용하여 난 친구와 함께 하나의 서비스를 만들었는데, 자꾸 나한테 ESLint 에서 경고와 오류가 있다는 것이었다. 그래서 도대체 이 ESLint가 무엇이냐 물어보니 "Typescript/Tsx 코드를 AST로 분석하는 정적 검사"라고 이야기 해줬다. 물론 나는 여전히 알아듣지 못해 AST는 뭐고 정적 검사는 뭐냐? 라고 물어봤는데 AST는 코드를 트리 구조로 변환하여, 변수 선언 노드를 찾고, 선언된 변수 이름을 기록하여 참조하는 노드가 있는지 확인하는 것처럼 동작하는데, 이를 추상 구문 트리라고 한다고 하고, 정적 검사는 프로그램을 실행하지 않은 상태에서 검사한다는 뜻이라고 했다.


위의 말을 들으니 내가 아직도 얼마나 코드에 대해 무지한지, 서비스 배포 과정에 대해 알지 못하는 부분이 많은 지 알 수 있었다. 그래서 배포하기 전에 각종 테스트를 하는 과정에 대해 공부하고자 블로그 하나를 보고 참고하기로 했다. 이 글은 내가 직접 블로그를 보고 정리하여 작성하였다.


# 테스트 자동화의 중요성
소프트웨어를 더욱 신속하고 품질 저하 없이 소비자들에게 제공하기 위해 자동화가 필요하고, 수동적이고 반복적인 작업에 시간을 허비하지 않기 위해 중요하다. 기존에는 테스터가 일관된 검사를 수행하게 테스트 스크립트에 의해 지정되는데, 사람은 지루함을 느끼기도 하고 그러다보면 실수로 이어지기 때문에 자동화를 시켜야한다. 


# 테스트 피라미드
테스트 자동화를 알기 위해서는 필수적인 개념으로, Mike Cohn이 고안한 개념이다. 
(images/testpyramid.png)

위의 그림은 총 세가지 단계로 구성되어 있다. 
1. 단위 테스트
2. 서비스 테스트
3. 사용자 인터페이스 테스트

현대적인 관점에서는 이 테스트 피라미드가 단순해 보일 수 있어 오해의 소지가 있을 수 있으나, 본질은 단순하기에 테스트를 구축할 때 도움이 된다. 여기서 두 가지를 기억하는 것이 좋다.
1. 다양한 테스트 작성
2. 상위 계층으로 갈수록 더 적은 테스트 작성

작고 빠른 단위 테스트를 많이 작성하는 것이 좋다. 처음부터 끝까지 테스트하는 높은 수준의 테스트보다 세분화된 테스트를 작성하고, 유지 관리가 어렵고 실행하는데 오래 걸리는 테스트를 작성하지 않게 주의하는 것이 좋다.

피라미드에서 각 계층의 이름에 너무 집착하지 말고, 서비스 테스트는 이해하기 어려운 용어이다. react, angular, ember.js  등과 같은 단일 페이지 애플리케이션 프레임워크의 시대에서는 UI 테스트가 피라미드의 최상위 레벨에 있을 필요가 없고, 모든 프레임워크에서 UI를 완벽하게 단위 테스트할 수 있다.


## 샘플 어플리케이션

이 글의 필자는 여러 계층에 대한 테스트가 포함된 spring-testing 저장소를 만들었는데, 깃허브에서 확인할 수 있다. 

이 앱에 대한 기능은 간단하게 세 개의 엔드포인트가 있는 REST 인터페이스를 제공한다.
1. GET /hello > "Hello World"를 항상 반환
2. GET /hello/{성} > 제공된 성을 가진 사람을 조회하고, 알려진 사람인 경우 "안녕하세요 {이름} {성}"을 반환.
3. GET /weather > 독일 함부르크의 현재 날씨 상태를 반환

그리고 시스템 구조는 아래와 같다.
(images/springservicestructure.png)
HTTP를 통해 호출할 수 있는 REST 인터페이스를 제공하고, 일부 엔드포인트의 경우 데이터베이스에서 정보를 가져온다. 그 외에는 외부 날씨 API를 호출해 현재 날씨 상태를 가져와 표시한다.


내부적으로는 전형적인 spring 아키텍쳐이다.
(images/springarchitecture.png)

- Controller 클래스는 REST 엔드포인트를 제공하고 HTTP 요청 및 응답을 처리
- Repository 클래스는 데이터베이스와 인터페이스하고 퍼시스턴스 스토리지에 데이터를 쓰고 읽는 작업을 처리
- Client 클래스는 다른 API와 통신하며, darksky.net 날씨 API에서 HTTPS를 통해 JSON을 가져옴
- Domain 클래스는 도메인 로직을 포함한 도메인 모델을 캡쳐

자주 사용하는 레이어가 누락된 것을 발견할 수도 있지만, 이 애플리케이션은 단순하기 떄문에 서비스 계층은 불필요하기 때문이다. 또한 필자는 사람들이 서비스 계층을 지나치게 많이 사용한다고 생각하기 때문이다. 이 Repo는 간단한 CRUD 기능을 제공하고, 단순하게 유지하기 위해 Spring Data를 사용한 것이다. Spring Data는 직접 롤링하는 대신 간단하고 일반적인 CRUD Repo 구현을 제공하고, 실제 Postgres를 사용하는 대신 테스트를 위한 인메모리 데이터베이스를 띄워주는 작업도 처리해준다.


## 단위 테스트

테스트의 기초는 단위테스트로 코드 베이스의 특정 단위가 의도한 대로 작동하는지 확인하는 테스트다. 모든 테스트 중 가장 범위가 좁고, 테스트의 수는 제일 많다.

## 단위란?
함수형 언어로 작업하는 경우 단위는 단일 함수가 될 가능성이 높다. 다양한 매개 변수를 사용하여 함수를 호출하고 예상되는 값을 반환하는지 확인하고, 객체 지향 언어에서는 단일 메서드부터 전체 클래스까지 다양할 수 있다. 


### 사교적이거나 고독한 단위 테스트
어떤 사람들은 완벽한 격리와 복잡한 테스트 설정을 피하기 위해 테스트 대상 주에의 모든 공동 작업자를 Mock 또는 Stub으로 대체해야한다고 주장하지만, 어떤 사람들은 속도가 느리거나 부작용이 더 큰 공동 작업자만 Stub이나 Mock 테스트를 해야한다고 주장한다. 모든 공동 작업자를 Stub 하는 테스트는 고독한 단위 테스트, 실제 공동 작업자와 대화할 수 있는 테스트는 사교적인 단위 테스트라고 부른다. 이 두 가지 방식을 중 어느 것을 할지 정하는건 중요하지 않고, 적재적소에 사용하는 것이 중요하다.


### Mocking과 Stubbing
Mock[^1]과 Stub[^2]은 서로 다른 두 가지 종류의 테스트 더블[^3]인데, 많은 사람들이 혼용해서 사용하지만 정확하게 구분하고 각각의 특성을 염두에 두는것이 좋다. 
클래스, 모듈 또는 함수 등의 실제 객체를 가짜 버전으로 대체한다는 뜻으로 가짜 버전은 실제처럼 보이고 작동하지만, 단위 테스트를 시작할 때 직접 정의한 미리 준비된 응답만 나온다. 
테스트 더블을 사용하는 것은 단위 테스트에만 국한되지 않고, 시스템의 전체 부분을 제어된 방식으로 시뮬레이션 할 수 있지만, 많은 최신 언어와 라이브러리를 통해 Mock과 Stub을 쉽고 편하게 설정할 수 있다. 특히나 어떤 기술을 선택하던 모형을 설정하는 방법을 제공할 가능성이 높고, 직접 모의 테스트를 작성하는 경우도 실제와 동일한 서명을 가진 가짜 클래스/모듈/함수를 작성하고 가짜를 설정하기만 하면 된다.
단위 테스트가 매우 빠르게 실행될텐데, 괜찮은 환경에서는 몇 분 안에 수천 개의 단위 테스트를 실행할 수 있고, 코드베이스의 작은 부분을 따로 테스트하고 데이터베이스, 파일 시스템 또는 HTTP 쿼리 실행을 피하면 테스트 속도를 빠르게 유지할 수 있다. 

### 무엇을 테스트 할 것인가?
단위 테스트는 기능이나 내부 구조의 어느 계층에 속해 있는지 관계 없이 모든 프로덕션 코드 클래스에 대해 작성할 수 있고, Repo, 도메인 클래스, 파일 리더를 단위 테스트하는 것 처럼 컨트롤러를 단위 테스트 할 수도 있다. 프로덕션 클래스 당 하나의 클래스 규칙을 준수하기만 하면 시작하기 수월하다.
단위 테스트 클래스는 최소한 클래스의 공용 인터페이스는 테스트 해야한다. 비공개 메서드는 다른 테스트 클래스에서 호출할 수 없어 테스트가 불가능하기 때문이다. 테스트 클래스의 패키지 구조가 프로덕션 클래스와 동일하다면, 테스트 클래스에서 보호되거나 패키지 비공개 메서드에 액세스가 가능하지만 이러한 메서드까지 테스트 하는 것은 내부 구조를 변경할 때 테스트가 깨질 수 있다.

단위 테스트를 작성할 때에는 경계가 있다.
- 사소하지 않은 모든 코드 경로를 테스트해야 한다.
- 구현과 너무 밀접하게 연결되면 안된다.

프로덕션 코드에 너무 근접하게 되면, 프로덕션 코드를 리팩토링 할 경우 단위 테스트가 중단되기 때문에 코드 변경에 대한 안전망 역할을 잃게 된다. 리팩토링할 때마다 실패하면 오히려 작업이 더 많아져 내부 코드 구조를 반영하지 말고, 관찰 가능한 동작을 테스트하는 것이 좋다. 
> 값 x와 y를 입력하면 메서드가 A 클래스를 먼저 호출하고 B 클래스를 호출한 후 A 클래스의 결과와 B 클래스의 결과를 더한 값을 반환할까?
위의 테스트 보다 아래의 테스트여야 한다.
> 값 x와 y를 입력하면 결과가 z가 될까? 


공부를 하다보니 어느덧 3시가 다되어가서 오늘은 여기까지 하고 이만 자러가봐야 겠다.




[^1]: Mock : 특정 객체의 함수가 호출되었는지, 몇 번 호출되었는지, 어떤 인자가 전달되었는지 등 객체 간의 상호작용을 검증할 때 사용한다.
[^2]: Stub : 특정 객체의 함수를 호출했을 때 테스트에 필요한 미리 정해진 값을 반환하도록 만든 테스트 대역이다.
[^3]: 테스트 더블 : 소프트웨어 개발 과정에서 사용되는 테스트 방법론 중 하나로, 일부분이 완전히 준비되지 않았거나 테스트하기 어려운 상황에서 대안으로 사용될 수 있는 가짜 컴포넌트를 의미한다.
